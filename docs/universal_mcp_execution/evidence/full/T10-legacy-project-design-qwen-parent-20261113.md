## Parent source check and limitations

1. **An alias cannot be inferred for every canonical ref.** `_runtime_state.py:90–101` normalizes a saved `true` only on the same-worker/server branch; `_managed_backend.py:436–448,637–650,1113–1129` then operate on the canonical key. Automatically deriving and trusting a `true` key for *every* later integer ref has no explicit indication that this particular ref was restored from a legacy boolean value. A stale or conflicting alternate row is a conditional risk, not evidence of an actual historical row. Any acceptance of the old attribution needs an exact, server-owned lineage from the persisted ref and a current identity check, rather than just JSON key shape or a caller-supplied project ID.
2. **Project policy check is necessary, not provenance proof.** `_project_authority.py:232–257,280–291` verifies the project record/workspace and checks host/service and project permission grants; the method's explicit inputs are only project ID and permission. It does not by itself prove the old ref/project association was originally authorized, nor does this source check establish an authenticated end-user principal. Preserve those as open obligations.
3. **An outer transaction cannot simply wrap today's methods unchanged.** `OperationStore` opens SQLite with `isolation_level=None` (`_operation_store.py:177–182`). `merge_metadata_fields` unconditionally issues its own `BEGIN IMMEDIATE` and `COMMIT` (`:4832–4866`), while `put_metadata` performs its own SQL under the store lock (`:4799–4830`). The proposal correctly calls for transaction-aware store changes, but a generic outer transaction around existing `save_runtime_state` is not a proven solution. Transaction ownership, lock order, lifecycle-field merge preservation, concurrent writers, commit/readback failures and rollback must be designed and tested rather than assuming reentrant locking implies nested SQLite transactions.
4. **Correct the failure ordering.** Existing `persist()` calls `save_runtime_state` *before* writing revision rows (`_managed_backend.py:1113–1129`); `save_runtime_state` separately writes the session then runtime (`_runtime_state.py:46–62`). Thus the concrete current sequential partial-write risk includes updated session/runtime metadata before some revision rows are updated. The child's example with a newly written first revision but an as-yet-unupdated session is not the directly established order of this function. No actual disk failure has been induced.
5. **Preflight has an identity limit.** `connect` calculates the endpoint key before `worker.start`, but the current path obtains instance/generation only from `runtime_metadata()` after `start` (`_managed_backend.py:1014–1048`). A conservative early conflict check may be useful, but before that metadata it cannot by itself establish the same-Worker continuity on which the suggested adoption relies. A precheck also needs a race-safe recheck/commit plan; the proposal's instruction to have no new failure after start cannot be guaranteed merely by moving one check. No existing Worker was started or stopped here.
6. **Writing a new canonical binding is a form of migration.** Leaving the old row in place does not make it read-only: `persist()` would write a new project-attributed canonical row. This is a proposed durable change, not permission to modify any old model, Worker, SSH session, UNKNOWN or real historical state. No such state was inspected or changed.

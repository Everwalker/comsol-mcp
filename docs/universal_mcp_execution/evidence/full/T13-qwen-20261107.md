## 2. 关键决策（两轮主 Agent 复核后的最终实现取向）

### 2.1 普通/嵌套实体删除：写前拒绝，不实现通用 remove

`ModelEntityList.remove(String)` 在官方 6.4 API 文档中的全部契约文字是 "Removes an entity."，没有后代范围、也没有 incoming 依赖范围说明；`NodeGroupList.remove(String)` 明确 "Also removes all group members from the model"；GUI 文档明确 Group 节点 Delete 会移除节点及其全部子节点，只有 Ungroup 才把子节点上移到父级。三份文档已用本机 COMSOL 6.4 KB 复核（本会话重新确认 sha256）：

- `doc/help/wtpwebapps/ROOT/doc/com.comsol.help.comsol/api/com/comsol/model/ModelEntityList.html` — sha256 `463ef0c4e8b2b7315e8950bd576f4b783718c75308307cef0a4d584d86b835ab`
- `.../api/com/comsol/model/NodeGroupList.html` — sha256 `39d28e1083da9a724501eb87b28f014ae7dbf1860f585a07eb80f36c2df47949`
- `.../comsol_ref_customizing.20.06.html` — sha256 `124c3564dd74aea33d3d43a6548f690641c696cd8391c252d9f97b7194ec249e`
  （同段落实证也见 `COMSOL_ReferenceManual.pdf`，sha256 `3dacc33243911a98cbcac19c6b83c9b662dd0b7c56b880b3a9e6a2ab602e7106`）

因此 `prepare_node_action` 在非 model-root NodeGroup 路径上，在任何 receiver 访问/任何写票之前抛 `PreWriteRefusal("API_UNSUPPORTED")`，details 精确列出未满足的证明义务：每 receiver 族的 remove(String) 后代范围公开契约、incoming expression/selection/consumer 图（尚未验证可用的公开 getter）、对任意 receiver 可证明完备的子节点枚举、写前的跨列表保留证明；并给出已复核替代路线（仅 model-root NodeGroup structural ungroup）。

同一分支保留 `cascade != false` 的拒绝（未改动）。已实现过又被撤销的通用 remove 未留在源码中：`execute_node_action` 的 node.remove 分支与 except 分支均为 HEAD 原样（仅 group adapter）。

### 2.2 22 个候选集合的 leaf 扫描不构成可删除证明（本会话再加严的证据）

`_collect_children` 只按 `COLLECTION_CANDIDATES`（实测 22 项：component, geom, mesh, physics, material, propertyGroup, func, variable, selection, coordSystem, cpl, pair, multiphysics, feature, study, sol, dataset, numerical, table, export, view, extraDim）探测 receiver。空扫描只是"这 22 个名字没有 tags"，不能证明任意 COMSOL receiver 没有未枚举的子集合或关联依赖；同时它已区分"自身 selection accessor"（`{collection:'selection', tag:None, accessor:True}`，不可独立删除）与带 tag 的子实体——这一区分本身由新增测试断言固定。

为了不让负控沦为同义反复，本会话把负控目标做成了扫描意义上的可证明 leaf（置空 selection accessor，并断言 `rows==[] and errors==[] and rpc_calls==len(COLLECTION_CANDIDATES)`），并另建一份包副本 /private/tmp/t13-mutant 重建"被否决的设计"（候选集 leaf 扫描 + 直接 `remove(tag)` + 事后 complete=false，脚本 /private/tmp/t13_mutate.py）：

- 副本上 4 个 T13 控制里 3 个失败（`3 failed, 1 passed`，被否决设计下拒绝不再发生）；
- 直接探针（/private/tmp/t13-mutant/tests/probe_cascade.py）实测：目标列表 `['b','a','c'] -> ['b','c']`，另一无关列表 `['b','a','c'] -> []`，而报告是 `success=True, complete=False, status=INCOMPLETE, applied=[target]`；
- 同探针在出货版源码副本上直接进入 `PreWriteRefusal`（进程非零退出，无任何 mutation）。

结论：same-list `order_before/after` + 事后 `complete=false` 无法撤回已发生的跨列表删除；出货契约在第一次 receiver 访问前拒绝。另需注意：本会话第一轮写的负控在副本上会"假通过"（fixture 目标的 `selection()` 被扫描记为 accessor 行，导致被否决设计也因"有子节点"而拒绝），已加严修正——这条弱判定的发现过程本身说明候选集 leaf 判定不可作为删除许可依据。

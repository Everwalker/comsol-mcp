# P0 bounded gap assessment: cached job-control registry routes

This is one bounded slice of the required 26-work-package / 272-action / 60-test / six-target inventory. It does not claim the full inventory is mapped or accepted.

## Findings

The source already had queue-independent `ControlDaemon` handlers for the exact cached operations `job.list`, `job.status`, `job.log`, `job.result`, `job.reconcile`, `job.wait`, and `job.cancel`. The missing production route was the registry fallback: `registry_call` and `operation_call` entered the serialized `ManagedBackend` queue, where these actions were not advertised as executable. This was a missing fallback entrypoint, not a missing implementation of the cached status/log/cancel handlers.

The fallback now validates each nested action with the catalog validator, rejects unsupported nested identity fields and unknown action arguments, and calls the same cached `_control_read` handler before the engine queue. Canonical dotted direct actions use the same validation and argument conversion, so their `cursor`/`filter` fields cannot be silently ignored; legacy underscore tools keep their existing `offset` signatures. The managed backend now refuses these cached operations if an internal caller bypasses the daemon router, so the registry capability cannot fall into model-scoped execution.

`job.list` accepts only the catalog selectors `status` and `project_id`; a filter object may use those fields without also supplying the same selector at top level. Its optional `cursor` is a decimal, zero-based offset string and is mutually exclusive with `offset`. `job.log` uses a decimal, zero-based event offset string as its cursor. The public operation description publishes these rules. `job.cancel` retains the existing authorization boundary: a normal cancel records intent without claiming that the solver stopped; `force_stop` requires explicit scoped authorization and ownership checks.

`job.cleanup` now has a conservative production route: callers must name job IDs explicitly; every selected job must be terminal and carry no known linked-job dependency. The implementation compacts only the duplicate job-row request/cache metadata and retains project selectors, the operation/idempotency row and result, the full job-event audit, and artifact/checkpoint metadata. It adds one `JobCacheCompacted` event. Repeated cleanup is a no-op. A supplied outer project ID is checked against each selected job's recorded project. It never removes formal files or automatically sweeps a project.

`job.resume` now has a bounded production implementation: only an explicitly opted-in direct/registry `study.run` with a backend-created source/checkpoint binding, no prior solution tags, no `FileResource` dependencies, exact model/job/checkpoint hashes, terminal-and-reconciled Worker requests, and current ModelRef/revision is admitted. It restarts the whole study from a fresh model tag; it does not continue COMSOL solver iterations. If the model revision or dirty state advanced after the pre-run save, the caller must provide an explicit `authorization_ref`; the original source ref and failed record remain intact. One native child solve succeeded after a clearly labeled injected parent failure, and the saved result reopened in two distinct fresh Workers with zero additional solves. This does not establish natural COMSOL failure recovery, response-loss idempotency on a live engine, or six-target acceptance; see the run08 failure, separate saved-MPH supplement, and `T057` supplementary record.

# 冻结范围与阻断政策

原00/01/02/03/04/05/06契约是全项目范围。此前“Closure”没有删除原必需项目；本次全量交付需要为它们逐项给出覆盖结论。但已经成立的限定批准不因代码还能改善就重开。

阻断只来自：
1. 原required在其适用范围确实未实现/未验证；
2. 有直接证据会误判错误模型、串用数据/模型/版本、破坏用户状态、越权读写/停机、泄露凭据，或核心接口不可用；
3. 最终交付/安装/恢复违反原契约。

新性能优化、代码风格、额外物理/算法、未在原目标的平台不升级为required。可以延期，但原明列目标不能因难就延期并宣布全量完成。

发现先分类为REQUIRED_GAP、REGRESSION_BLOCKER、EXTERNAL_BLOCKER、NONBLOCKING。必须关联原要求和证据；“P1”标签本身不够。BLOCKED不是PASS，API不存在、许可缺失和OS限制应依据原合同的条件语义分别报告，禁止一刀切改N/A。

阶段自测失败先修依赖范围，不妨碍其他独立任务推进。只剩外部条件时留下统一清单，避免反复请求同一信息或循环重试。最终被批准的明确条件范围以原合同为准，不通过新推断扩大物理校准承诺。

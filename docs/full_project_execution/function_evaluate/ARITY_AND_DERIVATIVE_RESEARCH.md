# `function.evaluate`: Interpolation arity compatibility and derivative route

**Implementation state:** the source-table arity fallback is implemented and software-tested. It has not been exercised by the production handler on a native COMSOL server after this change. Derivative sampling remains `NOT_IMPLEMENTED / API_UNSUPPORTED`; the candidate below is research only.

## Interpolation arity evidence and supported profile

The adapter first reads `Interpolation.nargs` through `hasProperty`, `getValueType`, and the matching typed getter. A positive `Int` remains authoritative. Both installed COMSOL API references say that `nargs` only declares the count when the interpolation data format is `spreadsheet` or the source is `resultTable`. The row is explicit in the installed 6.3 file at `C:\Program Files\COMSOL\COMSOL63\Multiphysics\doc\help\wtpwebapps\ROOT\doc\com.comsol.help.comsol\comsol_api_general.47.34.html`: `nargs`, `integer (1-3)`, default `1`, description “The number of function arguments if struct is spreadsheet or source is resultTable.” Its SHA-256 is `E6104EF5086099D1360518BD0936F2EEA4C6378786348AF8E3714FB33108F837`. The 6.4 `model.func()` reference says the same at local KB document `COMSOL 6.4 - model.func()`, chunks 16754–16755, SHA-256 `c0b0ddce365ed8da5a8d8e45818ab0b056e552aaa01c99ca22e1f8be7c1e0edf`.

The same 6.4 reference documents `source` values `table | file | resultTable | function`, defines `table` as the local point/value matrix, and describes `argunit` as the required units “for each argument.” The 6.4 Supported Functions and Settings table lists Interpolation `argunit` as `StringArray`, `nargs` as `Int`, `source` as `String`, and `table` as `StringMatrix` (COMSOL 6.4 help HTML `doc/help/wtpwebapps/ROOT/doc/com.comsol.help.comsol/comsol_api_fileformats.53.17.html`, chunk 16653, SHA-256 `61a7f018a01577054ad544176753aa475535d70a83b7c823565395f07c64f238`). The 6.4 Programming Reference lists `table` as an Nx2 string array and documents the conditional `nargs` semantics at PDF page 1252, chunk 119905, SHA-256 `5b7f23ad2eae77f59d71935f4f6c9b6b9ede380dc34da065181841e512bbc105`.

Both native fixture snapshots independently show the same minimal, unambiguous profile: `source="table"`, one-element `argunit=["1"]`, and no `nargs` property. COMSOL 6.3 Build 290 recorded it for `root.fe_interp_none` and `root.fe_interp_linear` in `windows_native_20260926_01/run63_02/summary.json`; the COMSOL 6.4 Build 293 snapshot recorded it in `run64_engine_04/summary.json`. The fixture hash was `6a704f654dc2b145f84cb881f699fc60980cf30624bafbd0d63fa11d7b7f38f4`. The 6.3 runner ended `FAILED`: its direct-value checker did not recognize the raw complex-pair result shape, and the old production handler then refused `Interpolation.nargs` as absent; the refusal was also misclassified as post-dispatch because that source predated the read-witness and `PreWriteRefusal` corrections. This snapshot supports the actual metadata observation only, not production or end-to-end acceptance. The 6.4 run completed with overall acceptance `FAIL`: direct COMSOL interpolation returned the expected interior/end-point values and linear extrapolation value, but the then-frozen production adapter rejected every interpolation case because it required `nargs`. The current fallback was added after that source freeze; the old run is not a pass for the new implementation.

The implemented fallback is deliberately limited to this profile:

1. `nargs` is absent (`PROPERTY_ABSENT`), rather than malformed or unreadable.
2. The resolved node reads back `source` as the exact string `table`.
3. The resolved node reads back `argunit` as a `StringArray` with exactly one string entry.
4. The returned arity is therefore `1`; the table dimensions and caller coordinate count are never examined to infer arity.

Missing/unknown source, non-`StringArray` units, zero entries, or multiple argument-unit entries fail closed. A node exposing multiple function names is rejected as `AMBIGUOUS_FUNCTION` before this fallback or any value evaluation. Other source/layouts continue to require readable `nargs`; no general Interpolation arity policy is claimed. The local-table profile matches the documented point/value representation and the real 6.3/6.4 metadata snapshots, while the explicit argument-unit metadata is the count evidence.

The successful managed sample also reads raw `argrange` for reporting, through `PropFeature.getDoubleMatrix(String)`. The exact Java 6.4 signature was verified from the installed `com.comsol.api_1.0.0.jar` with `javap`. The mutation witness now treats only `getDoubleMatrix(String)` as a read; missing arguments, non-string arguments, or additional arguments remain fail-closed. The managed Java-handle regression checks this exact dispatch and a clean unchanged ledger; the separate signature-classifier test checks the incorrect-signature negative controls, and unknown methods remain fail-closed.

The updated candidate is still software-only until a new frozen 6.3 and 6.4 run sends the current source through the managed `function.evaluate` route for the same table fixture. The required native outcome is `OBSERVED`, correct interior and endpoint values, expected `EVALUATION_ERROR` for non-extrapolating out-of-range samples (with independent `range_status`), preserved raw metadata, revision/fingerprint stability, and no import/refresh/run/solve or function-tree change. Known refusal on an unsupported source/layout must remain clean `API_UNSUPPORTED`.

## Derivative API feasibility

The eight native COMSOL 6.4 `ParamBase` candidates retained in `run64_engine_04/summary.json` were `subst(d(q,x))`, `subst(d(q,y))`, both repeated second derivatives, and the equivalent four `substval(...)` forms for `q(x,y)=2*x^2+3*x*y+5*y^2`. Every `evaluateComplex` request returned `com.comsol.util.exceptions.FlException: Illegal_operator_context`; its separate `evaluateUnit` call returned `1`. The production request now exits earlier as a clean `API_UNSUPPORTED` validation refusal with an all-read witness. Therefore these direct parser candidates are actually `PROBE_FAILED_API_UNSUPPORTED`, while the public derivative route remains `NOT_IMPLEMENTED`.

The 6.4 Built-In Operators documentation permits `d`, `pd`, `dtang`, and `frame.dt` in “model settings and results evaluation”; `d(expr,var)` differentiates with the documented chain-rule behavior (COMSOL 6.4 help HTML `doc/help/wtpwebapps/ROOT/doc/com.comsol.help.comsol/comsol_ref_definitions.21.039.html`, chunk 18093, SHA-256 `3dfc580beee9f1bbb51360251942056348d42b4e49f02eb191fb944cfd2e5ac9`). The 6.4 Analytic-function property table separately documents `dermethod=automatic|manual` and `argders` as `(argument, partial derivative)` pairs when manual (Programming Reference page 112, chunk 118300, SHA-256 `5b7f23ad2eae77f59d71935f4f6c9b6b9ede380dc34da065181841e512bbc105`). Neither source defines a pure `ParamBase` derivative-evaluation API or proves that derivative operators over a custom function argument are legal inside an Analytic function definition. `argders` is metadata used to control an Analytic function's derivatives, not a demonstrated getter for sampling a requested partial derivative. It also does not generalize to Interpolation.

The one bounded follow-up candidate is a **native probe only**: in a disposable no-solve model with the existing analytic `q`, create temporary Analytic features with symbolic expressions `d(root.q(x,y),x)`, `d(root.q(x,y),y)`, and nested `d(d(root.q(x,y),x),x)` / `d(d(root.q(x,y),y),y)`, each with declared arguments `x,y`. Evaluate the temporary functions only after the derivative expression has been defined symbolically; expected values at `(2,3)` are `17`, `36`, `4`, and `10`. This tests whether `d()` accepts the function arguments in an Analytic expression context, avoiding constant differentiation and finite differences. Record exact parser errors, output units, and before/after function tags. A `try/finally` cleanup must remove every temporary feature and be independently read back.

That candidate creates and removes COMSOL model features. It cannot run under the current pure-query revision-suppression rule or be wired into the current read-only `function.evaluate` effect contract without redesign. If it works, integration needs an explicitly approved effect/ledger strategy with serialized write ticket, revision, cleanup outcome, and unknown-state freeze; if it fails, keep derivatives unsupported and do not substitute numerical differencing. No engine was started for this research and no derivative production code was added.
